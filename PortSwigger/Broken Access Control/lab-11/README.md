<h2>2. Overview</h2>

This lab demonstrates an Insecure Direct Object Reference (IDOR) vulnerability, which is a type of Broken Access Control.

The application uses direct references to identify and retrieve user-specific resources. However, it does not properly verify whether the authenticated user is authorized to access the requested resource.

This creates a security weakness because an attacker may be able to manipulate object references and access information belonging to other users.

IDOR vulnerabilities commonly occur when applications expose internal identifiers through URLs, request parameters, or other client-controlled input without implementing proper authorization checks.

<h2>3. Objective</h2>

The objective of this lab is to identify and exploit an IDOR vulnerability that allows an authenticated user to access another user's information by manipulating a direct object reference.

The exercise demonstrates why applications must validate resource ownership and enforce authorization checks before providing access to user-specific information.

<h2>4. Vulnerability Explanation</h2>

Insecure Direct Object Reference (IDOR) occurs when an application uses user-controlled identifiers to access internal resources without properly verifying whether the authenticated user has permission to access them.

For example, an application may use an account identifier, document ID, or user ID to retrieve specific information.

If the application does not validate ownership or authorization, an attacker may be able to modify the identifier and access another user's private resources.

This vulnerability is a form of Broken Access Control and can result in unauthorized information disclosure, data modification, or account-related compromise.

<h2>5. Technical Methodology</h2>

<h3>5.1 Initial Reconnaissance</h3>

I accessed the PortSwigger lab application and logged in using the provided credentials.

After authentication, I explored the application's available functionality, particularly the features that displayed user-specific information.

The initial objective was to understand how the application identified resources and how it handled requests for user-specific data.

<h3>5.2 Vulnerability Investigation</h3>

I used Burp Suite to intercept and inspect the HTTP requests generated by the application.

During the investigation, I examined the request parameters, URLs, and resource identifiers used to retrieve information.

I identified that the application relied on a direct object reference to determine which resource should be returned.

I then investigated whether the application properly validated the authenticated user's permissions before providing access to the requested resource.

<h3>5.3 Exploitation</h3>

After identifying the potential weakness, I modified the relevant object reference in the intercepted HTTP request.

I changed the identifier to reference another user's resource and forwarded the modified request to the application.

The application processed the request and returned information belonging to another user without properly verifying authorization.

This demonstrated that the application was vulnerable to an Insecure Direct Object Reference (IDOR).

<h3>5.4 Verification</h3>

After submitting the modified request, I examined the server response to verify whether the requested resource could be accessed.

I confirmed that the application returned information belonging to another user despite the authenticated account not having permission to access it.

The successful completion of the lab demonstrated that the application did not properly enforce object-level authorization.

<h2>6. Findings</h2>

**Identified Vulnerability:** Broken Access Control – Insecure Direct Object Reference (IDOR)

**Root Cause:** The application relied on user-controlled object references without properly verifying whether the authenticated user was authorized to access the requested resources.

**Security Impact:** An attacker could potentially access private information or manipulate resources belonging to other users.

**Result:** Lab successfully completed.

<h2>7. Security Impact</h2>

Potential consequences include:

- Unauthorized access to other users' information.
- Exposure of sensitive personal data.
- Unauthorized retrieval of confidential resources.
- Unauthorized modification or deletion of user data.
- Privacy violations.
- Potential account compromise, depending on the resources exposed.

<h2>8. Recommended Remediation</h2>

To prevent this vulnerability, developers should:

1. Enforce authorization checks on the server side for every resource request.
2. Verify resource ownership before returning or modifying user-specific information.
3. Never rely solely on user-controlled identifiers to determine access permissions.
4. Implement object-level authorization checks on every relevant endpoint.
5. Apply the principle of least privilege.
6. Use indirect object references where appropriate, while still enforcing authorization.
7. Log and monitor suspicious attempts to access resources belonging to other users.
