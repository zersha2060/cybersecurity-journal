<h2>2. Overview</h2>

This lab demonstrates an Insecure Direct Object Reference (IDOR) vulnerability that results in unauthorized access to another user's information through a data leakage issue in an HTTP redirect response.

The application uses a user ID supplied through a request parameter to retrieve account information. However, it does not properly verify whether the authenticated user is authorized to access the requested account.

Although the application redirects users after processing the request, sensitive information may still be included in the redirect response.

This creates a security weakness because an attacker may be able to inspect the HTTP response and obtain information belonging to another user, even when the browser redirects to a different page.

<h2>3. Objective</h2>

The objective of this lab is to identify and exploit an IDOR vulnerability that allows access to another user's information through data exposed in an HTTP redirect response.

The exercise demonstrates why applications must enforce proper authorization checks and ensure that sensitive information is not exposed in HTTP responses, including redirects.

<h2>4. Vulnerability Explanation</h2>

Broken Access Control occurs when an application fails to properly enforce restrictions on the resources and information users are allowed to access.

In this scenario, the application relies on a user ID provided through a request parameter to identify which user's information should be retrieved.

If the application does not verify whether the authenticated user is authorized to access the requested account, an attacker may be able to manipulate the user ID parameter.

Additionally, the application may expose sensitive account information in an HTTP redirect response.

An HTTP redirect does not automatically prevent sensitive information from being disclosed. The response itself can still contain information that can be inspected using tools such as Burp Suite.

This vulnerability combines IDOR with information disclosure through an HTTP response.

<h2>5. Technical Methodology</h2>

<h3>5.1 Initial Reconnaissance</h3>

I accessed the PortSwigger lab application and logged in using the provided credentials.

After authentication, I explored the application's available functionality, particularly the user profile and account information features.

The initial objective was to understand how the application retrieved user information and handled HTTP redirects.

<h3>5.2 Vulnerability Investigation</h3>

I used Burp Suite to intercept and inspect the HTTP requests and responses generated by the application.

During the investigation, I examined the request parameters to identify whether the application used a user ID to retrieve account information.

I also inspected the server responses, particularly HTTP redirect responses, to determine whether sensitive information was exposed before the browser completed the redirection.

This revealed that the application could disclose user information through its redirect response without properly enforcing access control.

<h3>5.3 Exploitation</h3>

After identifying the potential weakness, I modified the user ID parameter in the intercepted HTTP request to reference another user's account.

I forwarded the modified request and examined the resulting HTTP response using Burp Suite.

Although the application returned a redirect response, the response contained information associated with the requested user.

This demonstrated that sensitive information could be retrieved by inspecting the HTTP response rather than relying only on what was displayed in the browser.

<h3>5.4 Verification</h3>

After modifying the request parameter, I examined the HTTP response in Burp Suite to verify whether information belonging to another user had been exposed.

I confirmed that the response disclosed the requested user's information despite the redirect behavior.

The successful completion of the lab demonstrated that the application did not properly enforce authorization and exposed sensitive information through an HTTP redirect response.

<h2>6. Findings</h2>

**Identified Vulnerability:** Broken Access Control – Insecure Direct Object Reference (IDOR) with Information Disclosure

**Root Cause:** The application relied on a user-controlled ID parameter without properly verifying authorization and exposed sensitive user information in an HTTP redirect response.

**Security Impact:** An attacker could potentially access private information belonging to other users by manipulating request parameters and inspecting HTTP responses.

**Result:** Lab successfully completed.

<h2>7. Security Impact</h2>

Potential consequences include:

- Unauthorized access to other users' information.
- Exposure of sensitive personal information.
- Information disclosure through HTTP responses.
- Privacy violations.
- Unauthorized retrieval of confidential account data.
- Potential account compromise, depending on the information exposed.

<h2>8. Recommended Remediation</h2>

To prevent this vulnerability, developers should:

1. Enforce authorization checks on the server side for every user-specific resource.
2. Verify resource ownership before processing requests.
3. Never rely solely on user-supplied IDs to determine access permissions.
4. Avoid including sensitive information in HTTP redirect responses.
5. Ensure that redirect responses contain only the information necessary for redirection.
6. Apply the principle of least privilege.
7. Log and monitor suspicious attempts to access other users' resources.
