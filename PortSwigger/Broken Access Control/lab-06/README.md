<h2>2. Overview</h2>

This lab demonstrates a Broken Access Control vulnerability in which access restrictions can be bypassed by changing the HTTP request method.

The application attempts to enforce access control based on the HTTP method used in a request. However, the application does not consistently apply authorization checks across different HTTP methods.

This creates a security weakness because an unauthorized user may be able to perform restricted administrative actions by modifying the HTTP method of a request.

<h2>3. Objective</h2>

The objective of this lab is to identify and exploit an access control weakness that allows a regular user to perform administrative actions by changing the HTTP request method.

The exercise demonstrates why authorization must be enforced independently of the HTTP method used to access an endpoint.

<h2>4. Vulnerability Explanation</h2>

Broken Access Control occurs when an application fails to properly enforce restrictions on what authenticated users are allowed to access or perform.

In this scenario, the application uses HTTP methods such as GET, POST, and other request methods to handle different operations.

However, the access control mechanism does not properly validate the user's permissions across all supported HTTP methods.

If authorization checks are applied inconsistently, an attacker may be able to bypass restrictions by changing the HTTP method while keeping the same endpoint and request parameters.

This vulnerability can allow unauthorized users to perform actions that should only be available to administrators.

<h2>5. Technical Methodology</h2>

<h3>5.1 Initial Reconnaissance</h3>

I accessed the PortSwigger lab application and logged in using the provided credentials.

After authentication, I explored the application's available functionality and examined how administrative operations were handled.

The initial objective was to understand how the application processed HTTP requests and enforced access restrictions.

<h3>5.2 Vulnerability Investigation</h3>

I used Burp Suite to intercept and inspect HTTP requests generated by the application.

During the investigation, I examined the HTTP methods used when performing administrative actions.

I focused on identifying whether the application enforced authorization consistently across different request methods.

The investigation revealed that the access control mechanism could be bypassed by using a different HTTP method for the same restricted operation.

<h3>5.3 Exploitation</h3>

After identifying the weakness, I intercepted the relevant administrative request using Burp Suite.

I modified the HTTP request method while preserving the relevant endpoint and request parameters.

I then forwarded the modified request to the application to determine whether the access restriction could be bypassed.

The application processed the request without properly enforcing the user's authorization level, demonstrating the method-based access control weakness.

<h3>5.4 Verification</h3>

After submitting the modified request, I examined the server response to determine whether the restricted administrative action had been successfully performed.

The successful completion of the lab demonstrated that the application's authorization mechanism did not consistently validate user permissions across different HTTP methods.

<h2>6. Findings</h2>

**Identified Vulnerability:** Broken Access Control – Method-Based Access Control Bypass

**Root Cause:** The application enforced access restrictions inconsistently across HTTP methods, allowing unauthorized users to bypass authorization checks by modifying the request method.

**Security Impact:** A regular user could potentially perform administrative operations without having the required privileges.

**Result:** Lab successfully completed.

<h2>7. Security Impact</h2>

Potential consequences include:

- Unauthorized execution of administrative operations.
- Bypass of access control restrictions.
- Unauthorized modification of application data.
- Privilege escalation.
- Unauthorized management of user accounts.
- Potential compromise of sensitive application functionality.

<h2>8. Recommended Remediation</h2>

To prevent this vulnerability, developers should:

1. Enforce authorization checks on the server side for every sensitive endpoint.
2. Apply consistent authorization policies regardless of the HTTP method used.
3. Validate user permissions before processing sensitive operations.
4. Avoid relying solely on HTTP methods to determine whether a user is authorized.
5. Apply the principle of least privilege.
6. Implement centralized access control mechanisms.
7. Log and monitor unauthorized attempts to perform restricted operations.
