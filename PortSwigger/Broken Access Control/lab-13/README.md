<h2>2. Overview</h2>

This lab demonstrates a Broken Access Control vulnerability in which the application relies on the HTTP Referer header to determine whether a user is authorized to access restricted functionality.

The application attempts to protect administrative operations by checking the Referer header included in incoming HTTP requests.

However, the Referer header is controlled by the client and can be modified by an attacker.

This creates a security weakness because an unauthorized user may be able to bypass access restrictions by manipulating the Referer header to make a request appear as though it originated from an authorized administrative page.

<h2>3. Objective</h2>

The objective of this lab is to identify and exploit a Referer-based access control vulnerability that allows a regular user to perform restricted administrative operations.

The exercise demonstrates why applications should never rely on client-controlled HTTP headers to make authorization decisions.

<h2>4. Vulnerability Explanation</h2>

Broken Access Control occurs when an application fails to properly enforce restrictions on what authenticated users are allowed to access or perform.

In this scenario, the application uses the HTTP Referer header to determine whether a request is authorized.

The Referer header indicates the address of the page from which a request originated. However, it is supplied by the client and can be modified using tools such as Burp Suite.

If the application trusts this header without independently verifying the authenticated user's permissions, an attacker may be able to bypass access restrictions.

This vulnerability demonstrates why authorization decisions must be based on trusted server-side information rather than client-controlled request headers.

<h2>5. Technical Methodology</h2>

<h3>5.1 Initial Reconnaissance</h3>

I accessed the PortSwigger lab application and logged in using the provided credentials.

After authentication, I explored the application's available functionality and examined how administrative operations were handled.

The initial objective was to understand how the application controlled access to restricted administrative functionality.

<h3>5.2 Vulnerability Investigation</h3>

I used Burp Suite to intercept and inspect the HTTP requests generated by the application.

During the investigation, I examined the HTTP headers included in requests to restricted administrative endpoints.

I specifically focused on the Referer header to determine whether the application used it as part of its access control mechanism.

The investigation revealed that the application relied on the Referer header to determine whether a request originated from an authorized administrative page.

<h3>5.3 Exploitation</h3>

After identifying the weakness, I intercepted the relevant administrative request using Burp Suite.

I examined the Referer header and modified its value to indicate that the request originated from the expected administrative page.

I then forwarded the modified request to the application.

The application accepted the request without properly verifying whether the authenticated user actually possessed administrative privileges.

This demonstrated that the Referer-based access control mechanism could be bypassed by manipulating a client-controlled HTTP header.

<h3>5.4 Verification</h3>

After forwarding the modified request, I examined the server response to determine whether the restricted administrative operation had been successfully performed.

I verified that the application accepted the request despite the authenticated user not having the required administrative privileges.

The successful completion of the lab demonstrated that the application relied on an untrusted HTTP header instead of enforcing proper server-side authorization.

<h2>6. Findings</h2>

**Identified Vulnerability:** Broken Access Control – Referer-Based Access Control Bypass

**Root Cause:** The application relied on the client-controlled HTTP Referer header to determine whether a user was authorized to perform administrative operations.

**Security Impact:** An unauthorized user could potentially bypass access restrictions and perform administrative actions by manipulating HTTP request headers.

**Result:** Lab successfully completed.

<h2>7. Security Impact</h2>

Potential consequences include:

- Unauthorized access to administrative functionality.
- Bypass of application access restrictions.
- Unauthorized modification of application data.
- Unauthorized management of user accounts.
- Privilege escalation.
- Potential compromise of sensitive application functionality.

<h2>8. Recommended Remediation</h2>

To prevent this vulnerability, developers should:

1. Never use the Referer header as the primary mechanism for authorization.
2. Enforce authorization checks on the server side for every sensitive endpoint.
3. Verify the authenticated user's permissions before processing administrative operations.
4. Derive user roles and privileges from trusted server-side session information.
5. Apply the principle of least privilege.
6. Implement centralized access control mechanisms.
7. Log and monitor unauthorized attempts to access restricted functionality.
